Cleaning and Transforming

Every cleaning choice is part of the analysis

Workflow
  1. Question
  2. Measure
  3. Collect
  4. Clean
  5. Describe
  6. Compare/Relate
  7. Interpret
  8. Act

No playtest export arrives ready to analyse. This page has two halves. The first is cleaning: finding missing values, duplicates, impossible values and broken labels, and dealing with each without quietly changing the answer. The second is transforming: the pipe and the six dplyr verbs that reshape a clean table into the one your question needs. The playtest question running through it: “Which build keeps players longer?”, and how a single line of cleaning nearly hides the answer.

Stage: 2 · Core. Time: 30 minutes in class; 20 more to work through the R. Before this: Distributions and Shape. Key terms: missing value, duplicate, key, impossible value, factor, cleaning log, pipe, verb, split–apply–combine. R you will write: is.na(), distinct(), trimws(), tolower(), factor(), filter(), select(), mutate(), arrange(), group_by(), summarise(), count(), n().

Learning Outcomes

By the end of these notes you can:

  • say what an NA means in a playtest export, and check whether the pattern of missing values is itself a finding;
  • find exact duplicates and duplicates on the key, and remove them with distinct();
  • tell an impossible value from an unusual one, and treat each correctly;
  • repair inconsistent category labels and convert text to numbers without losing data silently;
  • keep a cleaning log that records every row dropped and what it did to n;
  • chain filter(), select(), mutate(), arrange(), group_by() and summarise() with the pipe to answer a playtest question.

Why This Matters for Playtesting

Telemetry drops events when a build crashes. Spreadsheets get pasted into twice. Someone types “veteran” where the form said “Veteran”. Every one of these has to be dealt with before any summary means anything, and every way of dealing with it is a choice.

Cleaning choices change conclusions. Dropping the rows with a blank cell is one line of R. If the blanks are not scattered at random, that line removes a particular kind of player, and the summary you compute afterwards describes the players who were left. The worked example below does exactly this to the strongest finding in the Tidebreak data.

That is why cleaning goes in the report. A reader who cannot see what you removed cannot judge what you found. Cleaning is analysis (rule 6): record every choice where the reader can see it, not hidden in a script.

Part 1: Cleaning

You already know count(), mutate(), group_by() and summarise() from Stage 1. This part also uses filter(), which keeps the rows where a condition is true: raw |> filter(build == "A") is the Build A rows. Part 2 covers it properly.

The raw Tidebreak export is tidebreak_sessions_raw.csv. Load it so you see the file as delivered:

library(dplyr)
raw <- read_csv("data/tidebreak_sessions_raw.csv",
                trim_ws = FALSE, show_col_types = FALSE)
nrow(raw)
[1] 124

read_csv() normally strips spaces from the edges of text values without telling you. trim_ws = FALSE switches that off, so you see what a spreadsheet or database import would see.

Here is the whole cleaning process for this file, with the number of rows after each step. Every step is explained below.

Only one step removes rows. The others change values or decide to leave something alone, and they belong in the record just as much.

What NA Actually Means

NA is R’s marker for a missing value: a cell with nothing in it. It does not mean zero, and it does not mean the event did not happen. It means the export does not know. A blank deaths cell is not a player who never died.

NA is contagious. Any calculation that touches an NA returns NA, because R will not guess what the missing value was. Adding na.rm = TRUE tells R to leave the blanks out, which is itself a decision: it assumes the missing players look like the ones you can see.

colSums(is.na(raw))
       session_id         player_id            cohort         archetype 
                0                 0                 0                 0 
            build          accuracy          mobility     survivability 
                0                 0                 0                 0 
objective_control           support         awareness             score 
                0                 0                 0                 0 
            kills            deaths        objectives       shots_fired 
                0                 3                 0                 0 
     time_alive_s        distance_m   session_minutes       quit_reason 
                0                 0                 9                 0 
      wrong_turns   items_collected         completed        difficulty 
                0                 0                 0                 0 
        enjoyment           comment 
                0                 0 
mean(raw$deaths)
[1] NA
mean(raw$deaths, na.rm = TRUE)
[1] 3

is.na() returns TRUE for each blank cell, and colSums() adds them up column by column: a count of blanks in every column at once. The first mean() shows the contagion; the second is a decision.

Three questions, in this order, before you do anything to a missing value:

  1. How much is missing? A handful of blanks in 124 rows is different from half a column.
  2. Where is it missing? Split the count by build, cohort and outcome. If the blanks cluster, something produced them.
  3. Is the pattern the finding? A build whose quit path never writes the session length has a telemetry bug, and the players on that path are the ones the playtest was run to find (rule 9).

Common mistake: dropping every row with a blank, “to be safe”. You will see it done with na.omit(), drop_na() or complete.cases(). Count what it would remove before you ever do it:

sum(complete.cases(raw))   # rows with no blank anywhere
[1] 112

The worked example below shows what that one line would have cost.

Duplicates

A duplicate is a row that appears more than once. It inflates n, and it counts one player’s experience twice.

An exact duplicate repeats every column. It is almost always an export or copy-paste fault, and removing it is safe. A duplicate on the key repeats the identifier, here session_id, but may differ elsewhere. That is two records claiming to be the same session, and you have to work out which one is right before you remove either.

# Exact duplicates: how many rows disappear when repeats are removed?
nrow(raw) - nrow(distinct(raw))
[1] 4
# Duplicates on the key: which session IDs appear more than once?
raw |> count(session_id) |> filter(n > 1)
# A tibble: 4 × 2
  session_id     n
  <chr>      <int>
1 S046           2
2 S053           2
3 S057           2
4 S103           2
clean <- raw |> distinct()
nrow(clean)
[1] 120

distinct() keeps the first copy of every row and drops the repeats. Check both counts. Here 4 rows are exact copies and 4 session IDs are repeated: the same number, so every key duplicate is an exact copy and removing them is safe. If they did not match, you would look at the differing rows first.

Impossible Versus Unusual

An impossible value cannot happen in the game: a negative session length, a rating of 9 on a 1–7 scale, more objectives captured than the map has. It is an error. Fix it if you can trace the cause, otherwise set it to NA, and log it either way.

An unusual value is extreme but possible: a player who never died, a Sentinel who scored almost nothing. It is data. Removing it because it spoils a chart is deleting the players you most need to hear from.

The test is the game’s rules, not the chart. A boxplot flags points by distance from the rest. Only you know whether the game allows that value. Write the rule down, such as session_minutes > 0 or enjoyment in 1–7, then check the data against it:

clean |> filter(session_minutes <= 0) |> nrow()     # sessions of zero or less
[1] 0
clean |> filter(!enjoyment %in% 1:7) |> nrow()      # ratings off the 1-7 scale
[1] 0
clean |> arrange(score) |> select(session_id, archetype, score) |> head(5)
# A tibble: 5 × 3
  session_id archetype score
  <chr>      <chr>     <dbl>
1 S052       Sentinel    541
2 S046       Sentinel    579
3 S034       Sentinel    584
4 S059       Sentinel    587
5 S045       Sentinel    597

%in% asks “is this value one of these?”, and ! turns it round.

No impossible lengths or ratings. The five lowest scores are all Sentinels: unusual, not impossible, and they are the bimodal Sentinel finding from Describing Variables. They stay. The outlier decision tree is the same reasoning in diagram form.

Labels and Types

Inconsistent labels. R compares text exactly. "Veteran", "veteran" and "Veteran " with a trailing space are three different cohorts to count(), and a grouped summary will report three groups where the design had one. trimws() strips leading and trailing spaces and tolower() makes the case consistent. Use them together inside mutate(), and always count before and after:

clean |> count(cohort)
# A tibble: 13 × 2
   cohort         n
   <chr>      <int>
 1 " Novice"      1
 2 " Regular"     1
 3 " Veteran"     1
 4 "Novice"      30
 5 "Novice "      2
 6 "REGULAR"      3
 7 "Regular"     45
 8 "Regular "     3
 9 "VETERAN"      1
10 "Veteran"     27
11 "Veteran "     2
12 "regular"      1
13 "veteran"      3
clean <- clean |> mutate(cohort = tolower(trimws(cohort)))
clean |> count(cohort)
# A tibble: 3 × 2
  cohort      n
  <chr>   <int>
1 novice     33
2 regular    53
3 veteran    34

13 spellings become three cohorts.

Factors. A factor is a categorical variable that knows its possible values and their order. Setting the levels puts the cohorts in order of experience rather than the alphabet, and it makes a misspelled label visible: anything not in levels becomes NA rather than a fourth group (rule 3).

clean <- clean |>
  mutate(cohort = factor(cohort, levels = c("novice", "regular", "veteran")))
clean |> count(cohort)
# A tibble: 3 × 2
  cohort      n
  <fct>   <int>
1 novice     33
2 regular    53
3 veteran    34

Numbers stored as text. When one cell in a numeric column contains "n/a" or a comma decimal, read_csv() reads the whole column as text. as.numeric() converts it back, and turns every value it cannot read into NA with only a warning:

minutes_text <- c("12.9", "24.6", "n/a", "8,6")
as.numeric(minutes_text)
Warning: NAs introduced by coercion
[1] 12.9 24.6   NA   NA

A constructed example, since this export’s numbers all arrived as numbers. Two of four values became NA, and the only sign was a warning. Count the NAs before and after converting: any increase is data you just lost.

Keeping a Cleaning Log

A cleaning log is a list of every change made to the data, in order, with the number of rows before and after. It is short, and it goes in the report.

Step Rows after Why
Raw export 124 As delivered
Remove exact duplicates 120 4 sessions exported twice
Standardise cohort labels 120 18 values re-spaced or re-cased; no rows removed
Check impossible values 120 None found against the game’s rules
Keep blank session_minutes 120 All 8 are Build A frustration quits; see the worked example

A step that removes no rows still goes in the log. Relabelling changes which group a player is counted in, and the reader needs to know that happened.

For your project: start the cleaning log the day the first export arrives, in the same Quarto document as the analysis. It goes in the Methodology section of your report, and a reader should be able to reproduce your n from it.

Worked Example: the Blanks Are the Finding

Which build keeps players longer? After removing the 4 duplicates, 8 sessions have a blank session_minutes. Every one of them is Build A. Every one of them ended in a frustration quit.

clean |> count(build, quit_reason, missing = is.na(session_minutes))
# A tibble: 9 × 4
  build quit_reason     missing     n
  <chr> <chr>           <lgl>   <int>
1 A     Completed test  FALSE      31
2 A     Frustrated      FALSE      12
3 A     Frustrated      TRUE        8
4 A     Lost interest   FALSE       7
5 A     Technical fault FALSE       2
6 B     Completed test  FALSE      38
7 B     Frustrated      FALSE       5
8 B     Lost interest   FALSE      14
9 B     Technical fault FALSE       3

count() can count a condition as well as a column: missing = is.na(...) makes a TRUE/FALSE column and counts each combination.

That pattern is not random, so both obvious ways of handling it are wrong.

Choice 1: drop incomplete rows. complete.cases() keeps only rows with no blank anywhere. It keeps 109 of 120 sessions. Before, Build A had 20 frustration quits against Build B’s 5. After, it has 12 against 5. One line of cleaning removed 40% of the evidence for Build A’s biggest problem, and nothing warned you.

Choice 2: leave them out of the median. With na.rm = TRUE, Build A’s median session is 26.1 minutes. But the Build A frustration quits that were recorded have a median of 11.2 minutes. The missing sessions are almost certainly short ones, so leaving them out makes Build A look better than it is.

What the complete data says. For this exercise the unbroken export exists, so the damage can be measured. Build A’s true median is 23.2 minutes, not 26.1. The blank cells were never noise. They were the shortest, angriest sessions in the playtest, lost by a telemetry bug on exactly the path the playtest was meant to examine.

The defensible handling keeps the rows, counts them from quit_reason, which survived, reports the median with a note that 8 short sessions are missing from it, and files a bug against Build A’s session logging.

What should the team do? Fix the logger first, because the next playtest will have the same hole. Then report Build A’s frustration quits from the column that is complete, and say plainly which number is an overestimate and why.

Part 2: Transforming

A clean table is rarely the table your question needs. You need some of the rows, some of the columns, a new column computed from others, a different order, or one row per group. The dplyr package, part of the tidyverse, does each of these with one verb, and the pipe joins the verbs together.

The Pipe

You met the pipe in Stage 1. As a reminder, |> passes the result on its left in as the first argument of the function on its right:

With the pipe Means
x \|> f() f(x)
x \|> f(y) f(x, y)
x \|> f() \|> g() g(f(x))

Its value is in chaining. “The median session length of Build A’s frustration quits, to one decimal place”:

clean |>
  filter(build == "A", quit_reason == "Frustrated") |>
  pull(session_minutes) |>
  median(na.rm = TRUE) |>
  round(1)
[1] 11.2

It reads as a sentence: take the clean data, keep Build A’s frustration quits, pull out the session lengths, take the median, round it. Each line is one step, and deleting a line deletes one step. pull() extracts one column as a vector, the pipe-friendly version of $.

NoteGoing further: the same question without the pipe

You will see code written the other two ways. Both give the same answer.

# Nested: read from the inside out
round(median(clean$session_minutes[clean$build == "A" &
                                     clean$quit_reason == "Frustrated"],
             na.rm = TRUE), 1)
[1] 11.2
# Intermediate objects: clear, but leaves a trail of names
a_frus <- clean[clean$build == "A" & clean$quit_reason == "Frustrated", ]
round(median(a_frus$session_minutes, na.rm = TRUE), 1)
[1] 11.2

You will also see %>%, the older tidyverse pipe. It does the same job here. In RStudio, Ctrl+Shift+M types a pipe; Tools → Global Options → Code chooses which one.

The Six Verbs

Each verb takes a data frame first and returns a data frame, which is what makes them chain. To see what each one does, here is a small table of six sessions that every example below starts from:

few <- clean |>
  select(session_id, build, cohort, deaths, kills, session_minutes) |>
  head(6)
few
# A tibble: 6 × 6
  session_id build cohort  deaths kills session_minutes
  <chr>      <chr> <fct>    <dbl> <dbl>           <dbl>
1 S001       A     regular      4     7            NA  
2 S002       B     veteran      2     5            24.6
3 S003       A     regular      2     5            12.5
4 S004       B     novice       4     7            18.8
5 S005       A     veteran      3    12            18.7
6 S006       B     regular      5     7            25.3
Verb What it does The question it answers
select() Keep some columns “I only need these measures”
filter() Keep some rows “Only Build A”, “only the frustration quits”
mutate() Add or change a column “Kills per death”, “fix the labels”
arrange() Sort the rows “Shortest sessions first”
group_by() Mark the groups “For each build…”
summarise() One row of results per group “…what is the median?”

Inside every verb you refer to columns by their bare names, deaths rather than few$deaths: the verb already knows which table it is working on.

select(): keep columns

few |> select(session_id, build, deaths)
# A tibble: 6 × 3
  session_id build deaths
  <chr>      <chr>  <dbl>
1 S001       A          4
2 S002       B          2
3 S003       A          2
4 S004       B          4
5 S005       A          3
6 S006       B          5

Six rows, three columns. select(-cohort) would keep everything except cohort.

filter(): keep rows

few |> filter(build == "A", deaths >= 3)
# A tibble: 2 × 6
  session_id build cohort  deaths kills session_minutes
  <chr>      <chr> <fct>    <dbl> <dbl>           <dbl>
1 S001       A     regular      4     7            NA  
2 S005       A     veteran      3    12            18.7

Only the rows where every condition is TRUE. A comma between conditions means “and”; use | for “or”.

mutate(): add a column

few |> mutate(kd = round(kills / pmax(deaths, 1), 2))
# A tibble: 6 × 7
  session_id build cohort  deaths kills session_minutes    kd
  <chr>      <chr> <fct>    <dbl> <dbl>           <dbl> <dbl>
1 S001       A     regular      4     7            NA    1.75
2 S002       B     veteran      2     5            24.6  2.5 
3 S003       A     regular      2     5            12.5  2.5 
4 S004       B     novice       4     7            18.8  1.75
5 S005       A     veteran      3    12            18.7  4   
6 S006       B     regular      5     7            25.3  1.4

A new column, computed row by row from the others. pmax(deaths, 1) replaces a zero with 1 so that a player who never died does not divide by zero.

arrange(): sort

few |> arrange(desc(session_minutes))
# A tibble: 6 × 6
  session_id build cohort  deaths kills session_minutes
  <chr>      <chr> <fct>    <dbl> <dbl>           <dbl>
1 S006       B     regular      5     7            25.3
2 S002       B     veteran      2     5            24.6
3 S004       B     novice       4     7            18.8
4 S005       A     veteran      3    12            18.7
5 S003       A     regular      2     5            12.5
6 S001       A     regular      4     7            NA

Longest session first. Without desc() it sorts smallest first. arrange() puts NA last whichever way you sort.

group_by() and summarise(): one row per group

few |>
  group_by(build) |>
  summarise(sessions = n(), mean_deaths = mean(deaths))
# A tibble: 2 × 3
  build sessions mean_deaths
  <chr>    <int>       <dbl>
1 A            3        3   
2 B            3        3.67

Six rows in, one row per build out. group_by() changes nothing you can see; it marks the groups so that summarise() computes once for each. n() counts the rows in each group.

Chaining them

The verbs earn their keep together:

clean |>
  filter(build == "A", quit_reason == "Frustrated") |>
  mutate(logged = !is.na(session_minutes)) |>
  select(session_id, cohort, session_minutes, logged) |>
  arrange(session_minutes) |>
  head(4)
# A tibble: 4 × 4
  session_id cohort  session_minutes logged
  <chr>      <fct>             <dbl> <lgl> 
1 S117       regular             8.6 TRUE  
2 S043       novice              9.3 TRUE  
3 S097       novice              9.6 TRUE  
4 S039       regular            10.3 TRUE

Read it as a sentence: take the clean sessions, keep Build A’s frustration quits, add a column saying whether the length was logged, keep four columns, sort by length, show the first four. The shortest recorded quits come first, because the blank ones are sorted last.

Split–Apply–Combine

group_by() with summarise() does three things, which together are called split–apply–combine:

What is the average number of wrong turns in each build?

clean |>
  group_by(build) |>
  summarise(mean_wrong = mean(wrong_turns))
# A tibble: 2 × 2
  build mean_wrong
  <chr>      <dbl>
1 A           8.92
2 B           5.52

group_by() does the split, summarise() does the apply, and the combine is a table with one row per group.

The point of it shows when the question grows. How many sessions does each build have, how many are missing a length, and what is the median length of the rest?

clean |>
  group_by(build) |>
  summarise(
    n       = n(),
    missing = sum(is.na(session_minutes)),
    median  = median(session_minutes, na.rm = TRUE)
  )
# A tibble: 2 × 4
  build     n missing median
  <chr> <int>   <int>  <dbl>
1 A        60       8   26.2
2 B        60       0   27.1

One group_by(), as many summaries as you like. The answer is the worked example in one table: all 8 missing lengths are Build A’s, and the median beside them is computed without them.

You will also see tapply() and aggregate() doing split–apply–combine in older code. You do not need to write them.

Interpretation Guidance

What the data shows. The raw export has 4 duplicated sessions, 18 mislabelled cohorts and 8 blank session lengths, all in Build A frustration quits.

What the analysis suggests. Build A’s quit path does not write the session length. The blanks are a telemetry fault concentrated in the sessions that matter most.

What can legitimately be concluded. Build A’s frustration-quit count is reliable, because it comes from quit_reason, which is complete. Its median session length is an overestimate by an amount you cannot know from this export. Say both.

Report what you did, not only what you found. The cleaning log goes in the report’s Methodology section. A reader should be able to reproduce your n from it.

Common Mistakes

Dropping incomplete rows by reflex. na.omit() and complete.cases() are one line each and can remove the finding. Check where the blanks are first.

Treating NA as zero. A blank deaths cell is unknown, not a player who never died. Replacing it with 0 invents a very good player.

Using na.rm = TRUE without saying so. It is the right tool, and it changes what the number describes. Report how many values it left out.

Fixing labels without checking. Run count() before and after. A label you did not know about survives tolower().

Deleting unusual values as if they were impossible. The game’s rules decide what is impossible. The chart does not.

Forgetting to keep the result. clean |> filter(build == "A") prints the filtered rows and changes nothing. Assign it, a_only <- clean |> filter(...), to keep it.

Using = inside filter(). filter(build = "A") is an error; the comparison is ==.

Cleaning in a spreadsheet. Edits made by hand cannot be seen, repeated or reviewed. Every change belongs in code, where it runs again on the next export.

Practice

Each takes two or three minutes. Start from clean, the de-duplicated data with fixed labels from Part 1.

  1. Predict. Before running it: how many rows will clean |> filter(build == "B", quit_reason == "Frustrated") return? Use what you know from Planning a Playtest.
  2. Compute. Which rows have a blank session_minutes or a blank deaths? Count them by build and quit reason.
  3. Rewrite. You find tapply(clean$score, clean$archetype, median) in a teammate’s script. Rewrite it as a pipeline with group_by() and summarise(), and add the number of sessions per archetype.
  4. Critique. A teammate’s script starts clean <- na.omit(raw) and then reports Build A’s frustration rate. What is wrong, and what should the first lines of the script do instead?
NoteShow answers

1. Piping into nrow() counts the rows the filter kept:

clean |> filter(build == "B", quit_reason == "Frustrated") |> nrow()
[1] 5

5, the Build B frustration count from the worked example in Planning a Playtest.

2. | means “or”:

clean |>
  filter(is.na(session_minutes) | is.na(deaths)) |>
  count(build, quit_reason)
# A tibble: 3 × 3
  build quit_reason        n
  <chr> <chr>          <int>
1 A     Completed test     2
2 A     Frustrated         8
3 B     Lost interest      1

The 8 Build A frustration quits are the blank lengths; the blank deaths cells are scattered across other outcomes. Those two groups need different handling, and dropping every incomplete row treats them the same.

3.

clean |>
  group_by(archetype) |>
  summarise(n = n(), median_score = median(score))
# A tibble: 4 × 3
  archetype     n median_score
  <chr>     <int>        <dbl>
1 Duelist      30        1426.
2 Engineer     30        1472.
3 Scout        30        1546 
4 Sentinel     30        1528.

Adding n = n() costs one argument. Always report n next to a group summary (rule 8).

4. na.omit() drops every row with any blank, which removes all 8 of Build A’s unlogged frustration quits, so the reported frustration rate is too low. The script should remove duplicates, fix labels, then count the missing values by build and outcome before deciding anything, and log each step.

Summary

  • NA means unknown. Count it, find where it is, and ask whether the pattern is the finding before doing anything to it.
  • Check duplicates both exactly and on the key.
  • Impossible values are errors; unusual values are data. The game’s rules decide which is which.
  • trimws() and tolower() fix labels; factor() fixes their order; count() checks the result.
  • Keep a cleaning log with n at every step. It goes in the report.
  • The pipe passes its left side in as the first argument on its right, so a pipeline reads in the order things happen.
  • The six verbs select columns, filter rows, mutate columns, arrange rows, and group and summarise. group_by() + summarise() is split–apply–combine.
  • In Tidebreak, the 8 blank cells were the frustration quits. Dropping them would have hidden Build A’s worst problem.
Key term Meaning
Missing value (NA) A value that should exist but was not recorded
Exact duplicate A row repeated in every column
Key The column that identifies a row, such as session_id
Impossible value A value the game’s rules do not allow: an error
Unusual value An extreme but possible value: data
Factor A categorical variable with fixed, ordered levels
Cleaning log Every change to the data, in order, with n after each
Pipe (\|>) Passes the result on its left as the first argument on its right
Verb A dplyr function that takes a data frame and returns one
